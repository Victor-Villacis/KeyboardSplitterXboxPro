# M6.5 spike — DS4 personas and the 4-player cap (measured 2026-08-04)

Run on the cabinet with `cargo run -p ksx-output --example ds4_slot_probe`,
against ViGEmBus 1.21.442.0, while a `ksx daemon` session already held four
X360 pads.

## Result 1 — the strategic question, ANSWERED: DS4 pads are not capped at 4

```
baseline: 0 Sony DS4 HID node(s) present
baseline: 4 XInput slot(s) occupied      <- the daemon's X360 pads
pads 0..5: plugged, ready                <- SIX DualShock4Wired targets
--- RESULT ---
DS4 targets plugged : 6
Sony HID nodes seen : 12                 <- 2 nodes per pad, all six enumerated
XInput slots taken  : 4 (baseline 4)     <- UNCHANGED
```

Six DS4 targets plugged and enumerated **while four X360 pads already held every
XInput slot**, and the XInput count did not move. So:

- **ViGEm DS4 targets are plain HID devices.** They neither consume nor compete
  for XInput's four slots.
- **>4 players is a ViGEmBus feature**, not a HIDMaestro project. This
  contradicts `docs/ENHANCEMENTS.md` E4 and `research/virtual-gamepad-2026.md`
  :215, both of which routed >4 through HIDMaestro or vJoy and never considered
  ViGEm DS4. **Amend E4.**
- The natural cabinet shape is now: **slots 1–4 as X360 (genuine XInput, maximum
  game compatibility), slots 5+ as DS4 (HID/DirectInput)** — one driver, already
  installed, no second stack, no protocol client to write.
- Consumers of slots 5+ must read DirectInput/HID/SDL (MAME, RetroArch, Steam
  Input all do). An XInput-only game will still see four pads; that is Windows,
  not ksx.

## Result 2 — the blocker: `IOCTL_DS4_SUBMIT_REPORT` fails

Every pad plugged and reached ready, then rejected its very first report:

```
pad 0..5: plugged, ready, update FAILED: WinError(259)   // ERROR_NO_MORE_ITEMS
```

So today ksx can *create* DS4 pads but cannot *drive* them. Investigated far
enough to rule out the obvious:

- `DS4Report` is `#[repr(C)]`; `DS4SubmitReport { Size, SerialNo, Report }` is
  shaped **identically** to `XUsbSubmitReport`, whose IOCTL works on this same
  machine and driver. Sizes compute as expected (report 10, submit 20).
- `Size` is `size_of::<DS4SubmitReport>()`, matching the X360 path.
- The IOCTL code (`0x2AA80C`) and target type (2) come straight from the
  vendored client and are the documented values.

`ERROR_NO_MORE_ITEMS` is an odd verdict for a submit; it reads more like a
queue/ownership state than a marshalling error. This is the vendored client's
**never-exercised** path — upstream ships no DS4 example and no DS4 test — so
the next step is to diff our call against ViGEmBus's kernel handler for
`IOCTL_DS4_SUBMIT_REPORT` (target lookup, file-object ownership, whether a DS4
target needs something between `wait_ready` and the first submit) rather than to
guess at the struct.

## What this means for the roadmap

| Question | Answer |
|---|---|
| Is >4 players cheap? | **Yes** — ViGEm DS4, no new driver |
| Is HIDMaestro still needed? | Only for **DualSense / Switch Pro / Xbox Series** personas (M8), not for player count |
| Can we ship a DS4 persona today? | **Yes** (2026-08-04) — submit fixed (driver startup window, see `vigem-client/src/ds4.rs`), plumbing landed |
| Effort remaining | None for DS4; M8/HIDMaestro only for DualSense/Switch Pro/Xbox Series |

## Reproducing

`crates/ksx-output/examples/ds4_slot_probe.rs`. It plugs six pads, counts what
each subsystem sees, unplugs on exit (verified: 0 DS4 nodes left behind), and
installs nothing.
